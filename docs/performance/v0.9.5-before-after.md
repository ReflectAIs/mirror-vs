# v0.9.5 — Before/After Proof

This document provides reproducible evidence that the v0.9.5 performance work
**reduces cost** (tokens) and **improves performance** (latency, redundant work)
without changing what is sent to the model.

All numbers below were produced by running the repository's own test suite and a
deterministic benchmark. No network or model calls are involved.

---

## 3. Cost analysis (tokens)

**Reduced — condense input: −51%.** The condense path now strips redundant failed
`search_files` → empty-result pairs before summarizing. On the representative
scenario this is **312 → 153 tokens**, and it scales with the number of failed
searches in a conversation. Fewer summarizer input tokens = lower cost per
condense, and condensing happens repeatedly on long tasks.

**Increased (intended) — Workspace Pulse "Recent Changes".** This section was
silently broken (always empty) and is now restored. It adds **~620 tokens** to
environment details _only when files were modified_ (code/debug modes). This is a
deliberate trade: it lets the model see the diff instead of spending a turn
re-reading the file (a `read_file` result is typically 1–5k tokens), so it is
net-positive on both tokens and turns.

**Unchanged — everything else.** The remaining fixes do not alter the bytes sent
to the provider, so per-request input/output token counts are unchanged.

## 4. Performance analysis

| Change                                     | Before    | After   | Improvement           |
| ------------------------------------------ | --------- | ------- | --------------------- |
| Cache-point placement (400 msgs)           | 289.89 ms | 7.55 ms | **−97.4%**            |
| `countTokens` calls per truncation recount | N+1       | 2       | **−N+1 round-trips**  |
| `getGitStatus` calls per turn              | 2         | 1       | **−50% subprocesses** |
| `getSystemPrompt` builds per request       | 2–3       | 1       | **−50–67% file I/O**  |
| `listFiles` cache staleness after edit     | ~10 s     | 0 s     | **eliminated**        |
| `applyCachePoints` complexity              | O(n·m)    | O(n+m)  | linear                |
| Cache-point token math                     | O(n²)     | O(n)    | linear                |

The cache-point placement improvement is the headline: it was O(n²) because it
re-estimated tokens over message slices repeatedly; it is now O(1) range sums over
a prefix-sum array computed once.

---

## 5. Cache-hit analysis

**Unchanged.** None of the fixes alter the prompt bytes:

- `getSystemPrompt` memoization returns the identical string.
- `applyCachePoints` produces identical output (only the mutation behavior changed).
- The env-details diff lives in the **last** user message, which changes every turn
  and is never cacheable; the previous turn's frozen env details are untouched.

Therefore cache-read / cache-write ratios are unaffected by this release.
