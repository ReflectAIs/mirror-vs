# Boomerang Tasks (Subtasks)

Ever wished you could clone yourself? Boomerang tasks are the next best thing. They let Mirror VS's Orchestrator mode throw tasks to specialized modes, wait for them to come back, and weave everything together. Like a boomerang, but for code.

## What Are Boomerang Tasks?

Boomerang tasks (also called subtasks) are a way for Mirror VS to delegate work. The Orchestrator mode can spin off a subtask to, say, Code mode, let it do its thing, and then pick up the result when it's done.

Think of it like being the project manager who actually knows how to code:
- **You (or Orchestrator)** define *what* needs to happen
- **The subtask mode** figures out *how* to do it
- **The result** comes back to you, ready to integrate

### Why Would You Want This?

- **Different problems, different tools.** Architect mode plans, Code mode builds, Debug mode fixes bugs. Let each mode do what it does best.
- **Parallel-ish work.** Okay, it's not true parallelism, but it sure beats context-switching manually.
- **Separation of concerns.** Each subtask gets its own fresh context, so there's no cross-contamination between wildly different tasks.
- **Focused attention.** Each mode gets a clean slate — no baggage from whatever you were doing before.
- **Modular results.** Subtask outputs are discrete, making them easier to review and integrate.

## How It Works

### The Flow

1. **Orchestrator identifies** a piece of work that's better handled by a specialized mode
2. **Orchestrator creates a subtask** with clear instructions and assigns it to the appropriate mode
3. **The specialized mode** takes over, does the work, and completes the subtask
4. **Orchestrator picks up** the result and continues with the bigger picture

```
Orchestrator says: "I need a database schema. Code mode, you're up."
Code mode: *designs schema, writes migrations, reports back*
Orchestrator: "Excellent. Now, back to the architecture..."
```

### Mode Compatibility

Boomerang tasks work best when the target mode has the right tools for the job. Here's who pairs well with what:

| Mode | Best For | Has Tool Access? |
|------|----------|:---:|
| Code Mode | Implementation, refactoring | ✅ Full |
| Architect Mode | Planning, design, diagrams | ✅ Full (no code exec) |
| Debug Mode | Bug fixing, investigation | ✅ Full |
| Ask Mode | Research, questions | ✅ Read-only |

:::tip
The Orchestrator mode is intentionally limited to focus on high-level workflow management. It relies on boomerang tasks to do the actual heavy lifting — which is exactly the point.
:::

## Configuration

### Enabling Subtask Features

Subtasks respect the same [auto-approval settings](/features/auto-approving-actions) as the rest of Mirror VS. You can configure:

- **Auto-approve subtask creation** — Let Orchestrator spin off tasks without asking
- **Auto-approve subtask completion** — Let results flow back without manual intervention

### JSON Override for Orchestrator Mode

Want to give Orchestrator mode some extra capabilities? You can override its tool access via custom mode configuration:

```json
{
  "slug": "orchestrator",
  "name": "Orchestrator",
  "roleDefinition": "You are an expert project orchestrator...",
  "groups": [
    "read",
    ["edit", { "fileRegex": "" }],
    "command",
    "mcp"
  ]
}
```

## Best Practices

### Writing Good Subtask Instructions

A good subtask instruction is like a well-written ticket — clear, specific, and actionable:

- **State the goal clearly:** "Create a REST API endpoint for user registration"
- **Provide context:** Reference relevant files or decisions already made
- **Set boundaries:** "Don't modify the database schema — that's handled separately"
- **Specify the mode:** "This should be done in Code mode"

### When to Use Boomerang Tasks

- **Complex multi-step features** — Architecture → Backend → Frontend → Review
- **Investigating bugs** — Let Debug mode investigate while you (or Orchestrator) plan the fix
- **Research tasks** — Have Ask mode research API docs while you keep coding
- **Documentation generation** — Spin off docs generation to keep the main task focused

## Limitations

- Boomerang tasks run sequentially, not in parallel. One subtask completes before the next starts.
- Each subtask starts with a clean context — it doesn't inherit the parent's conversation history.
- The Orchestrator must wait for subtask completion before proceeding.
- Subtask depth is limited to prevent infinite delegation loops (yes, that's a thing that could happen).
