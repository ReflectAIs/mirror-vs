# Customizing Modes

Mirror VS lets you create **custom modes** — specialized AI personas for specific tasks or workflows. Want a mode that only writes documentation? A mode that only reviews code? A mode that's terrified of making changes and needs your explicit permission for everything? You can build all of that.

Custom modes can be **global** (available across all your projects) or **project-specific** (defined within a single project).

:::tip Sticky Models for Efficient Workflow
Each mode — including custom ones — remembers the last model you used with it. This means you can assign different preferred models to different tasks without constant reconfiguration. Switch modes, and Mirror automatically switches models. It's like having a personal assistant for your AI assistant.
:::

:::info Discover Modes
Looking for ready-to-use custom modes? Visit the [Mirror VS Marketplace](/features/marketplace) to browse and install modes with a single click. The marketplace offers specialized modes for React development, documentation writing, testing, and more.
:::

## Why Use Custom Modes?

- **Specialization:** Create modes optimized for specific tasks — "Documentation Writer," "Test Engineer," "Refactoring Expert" — whatever your workflow needs
- **Safety:** Restrict a mode's access to sensitive files or commands. A "Review Mode" could be read-only, so it's all eyes and no hands
- **Experimentation:** Safely experiment with different prompts and configurations without affecting other modes
- **Team Collaboration:** Share custom modes with your team to standardize workflows

## What's Included in a Custom Mode?

Custom modes are defined by several key properties. Here's what makes up a mode:

| UI Field / YAML Property                 | What It Does |
| ---------------------------------------- | ------------ |
| Slug (`slug`)                            | A unique internal identifier for the mode (letters, numbers, and hyphens only) |
| Name (`name`)                            | The display name you'll see in the Mirror VS UI |
| Description (`description`)              | A short summary shown in the mode selector so you know what it's for |
| Role Definition (`roleDefinition`)       | The core identity and expertise — defines Mirror's personality in this mode |
| Available Tools (`groups`)               | Which tool groups the mode can access (read, edit, command, mcp) |
| When to Use (optional) (`whenToUse`)     | Guidance for Mirror's automated decision-making and mode orchestration |
| Custom Instructions (optional) (`customInstructions`) | Specific behavioral guidelines or rules |

## Import/Export Modes

Easily share, back up, and template your custom modes. Export any mode — and its associated rules — into a single, portable YAML file that you can import into any project.

### Key Features
- **Shareable Setups**: Package a mode and its rules into one file for easy team sharing
- **Easy Backups**: Save your custom mode configurations so you never lose them
- **Project Templates**: Create standardized mode templates for different project types
- **Simple Migration**: Move modes between global settings and specific projects effortlessly
- **Flexible Slug Changes**: Change mode slugs in exported files without manual path editing

---

### Use Case

**Before**: Manually recreating custom modes and copying `.mirror/rules-{slug}/` folders for each new project or team member. Changing slugs required manual path updates.

**With this feature**: A single click exports a mode and all its rules to a YAML file. Another click imports it, setting everything up automatically. Change the slug in the exported file and the import process handles path updates.

### How it Works

The import/export functionality is managed from the **Modes** view.

![Mode Export and Import Buttons](/img/custom-modes/custom-modes-5.png)

#### Exporting a Mode
1. Navigate to the **Modes** view
2. Select the mode to export
3. Click the **Export Mode** button (download icon)
4. Choose a save location for the `.yaml` file

Mirror packages the mode's configuration and any rules from `.mirror/rules-{slug}/` into the YAML file.

#### Importing a Mode
1. Click the **Import Mode** button (upload icon) in the **Modes** view
2. Select the mode's YAML file
3. Choose the import level:
    ![Import Level Dialog](/img/custom-modes/custom-modes-6.png)
    - **Project**: Mode available only in the current workspace, saved to `.mirrormodes`
    - **Global**: Mode available in all projects, saved to global settings

**Note:** When exporting modes with rules, all file paths use forward slashes for cross-platform compatibility.

---

### Exported YAML File Format

```yaml
customModes:
  - slug: "my-custom-mode"
    name: "My Custom Mode"
    roleDefinition: "You are a helpful assistant."
    groups: ["read", "edit"]
    rulesFiles:
      - relativePath: "rules-my-custom-mode/rules.md"
        content: "These are the rules for my custom mode."
```

### Changing Slugs on Import

1. Export a mode with slug `original-mode`
2. Edit the YAML file and change the slug to `new-mode`
3. Import the file — the import process updates rule file paths to match

### FAQ

**"What happens if I import a mode with the same slug as an existing one?"**
The existing mode gets overwritten. Keep that in mind.

**"What's the difference between Global and Project imports?"**
**Global** modes work across all VS Code projects. **Project** modes are specific to the workspace where they're imported.

**"Can I export built-in modes like Code or Architect?"**
Yes. If you've customized a built-in mode, you can export it to save your changes.

**"What happens to rules when importing at the Global level?"**
Rules are stored in `~/.mirror/rules-{slug}/` instead of the project-specific folder.

**"How does slug change work?"**
Change the slug in the exported YAML, and the import process updates all rule file paths automatically.

## Methods for Creating and Configuring Custom Modes

### 1. Ask Mirror! (Recommended)

The easiest way: just ask Mirror to create a mode for you:

```
Create a new mode called "Documentation Writer". It should only be able to read files and write Markdown files.
```

Mirror VS will guide you through the process, prompting for necessary details. For fine-tuning later, use the Modes page or manual config.

### 2. Using the Modes Page

1. **Open the Modes page:** Open Mirror VS panel → click Mode menu → click the <Codicon name="settings-gear" />
2. **Create New Mode:** Click the <Codicon name="add" /> button
3. **Fill in Fields:**

<img src="/img/custom-modes/custom-modes-4.png" alt="Custom mode creation interface" width="600" />

*The custom mode creation interface showing fields for name, slug, description, role definition, tools, and instructions.*

4. Click "Create Mode". Mirror saves it in YAML format.

### 3. Manual Configuration (YAML & JSON)

Direct editing gives you the most control. Mirror VS supports both YAML (preferred) and JSON.

- **Global Modes:** Edit `custom_modes.yaml` or `custom_modes.json` — click "Edit Global Modes" from the Modes page
- **Project Modes:** Edit `.mirrormodes` (YAML or JSON) in your project root — click "Edit Project Modes (.mirrormodes)"

**YAML Example (`custom_modes.yaml` or `.mirrormodes`):**
```yaml
customModes:
  - slug: docs-writer
    name: 📝 Documentation Writer
    description: A specialized mode for writing and editing technical documentation.
    roleDefinition: You are a technical writer specializing in clear documentation.
    whenToUse: Use this mode for writing and editing documentation.
    customInstructions: Focus on clarity and completeness in documentation.
    groups:
      - read
      - - edit
        - fileRegex: \.(md|mdx)$
          description: Markdown files only
  - slug: another-mode
    name: Another Mode
```

**JSON Alternative (`custom_modes.json` or `.mirrormodes`):**
```json
{
  "customModes": [
    {
      "slug": "docs-writer",
      "name": "📝 Documentation Writer",
      "description": "A specialized mode for writing and editing technical documentation.",
      "roleDefinition": "You are a technical writer specializing in clear documentation.",
      "whenToUse": "Use this mode for writing and editing documentation.",
      "customInstructions": "Focus on clarity and completeness in documentation.",
      "groups": [
        "read",
        ["edit", { "fileRegex": "\\.(md|mdx)$", "description": "Markdown files only" }]
      ]
    }
  ]
}
```

### YAML/JSON Property Details

#### `slug`
- **Purpose:** A unique identifier for the mode
- **Format:** Must match `/^[a-zA-Z0-9-]+$/` (letters, numbers, and hyphens only)
- **Usage:** Used internally and for rule file directories (`.mirror/rules-{slug}/`)

#### `name`
- **Purpose:** The display name in the Mirror VS UI
- **Format:** Can include spaces, emojis, and proper capitalization

#### `description`
- **Purpose:** A short, user-friendly summary shown below the mode name in the selector UI
- **Format:** Keep it concise and focused on what the mode does

#### `roleDefinition`
- **Purpose:** Detailed description of the mode's role, expertise, and personality
- **Placement:** Placed at the beginning of the system prompt
- **Tip:** Make this detailed — it defines how Mirror behaves in this mode

#### `groups`
- **Purpose:** Array defining which tool groups the mode can access
- **Available Groups:** `"read"`, `"edit"`, `"command"`, `"mcp"`
- **Structure:**
  - Simple string for unrestricted access: `"edit"`
  - Tuple for restricted access: `["edit", { fileRegex: "pattern", description: "optional" }]`

#### `whenToUse`
- **Purpose:** (Optional) Guidance for Mirror's automated decision-making
- **Note:** Not displayed in the mode selector UI — that's what `description` is for

#### `customInstructions`
- **Purpose:** Additional behavioral guidelines for the mode
- **Placement:** Added near the end of the system prompt

### Benefits of YAML Format

YAML is the preferred format for several reasons:

- **Readability:** Indentation-based structure is easy on the eyes
- **Comments:** Add `#` comments to annotate your mode definitions
- **Multi-line Strings:** Clean syntax using `|` (literal) or `>` (folded) blocks
- **Less Punctuation:** Fewer commas and braces = fewer syntax errors
- **Editor Support:** Most editors provide excellent YAML highlighting

While JSON is still fully supported, new modes created via the UI or by asking Mirror default to YAML.

#### Tips for Working with YAML

- **Indentation is Key:** Use spaces, not tabs. This is the #1 source of YAML errors
- **Colons:** Keys need a colon and a space (`slug: my-mode`)
- **Hyphens:** List items start with `- ` (hyphen + space)
- **Validate:** Use an online YAML validator if you hit issues

### Migration to YAML Format

- **Global Modes:** Mirror VS automatically migrates `custom_modes.json` to `custom_modes.yaml` on startup if only the JSON file exists
- **Project Modes (`.mirrormodes`):** No automatic migration — manual conversion required. If you edit a project mode through the UI, Mirror saves it in YAML, effectively converting it

## Mode-Specific Instructions via Files/Directories

You can provide mode-specific instructions using files or directories in your workspace.

**Preferred Method: Directory (`.mirror/rules-{mode-slug}/`)**
```
.
├── .mirror/
│   └── rules-docs-writer/
│       ├── 01-style-guide.md
│       └── 02-formatting.txt
└── ...
```

**Fallback Method: Single File (`.roorules-{mode-slug}`)**
```
.
├── .roorules-docs-writer
└── ...
```

**Precedence:**
1. Directory method (`.mirror/rules-{mode-slug}/`) takes precedence if it exists and has files
2. If not, Mirror looks for `.roorules-{mode-slug}` as fallback
3. Content from files is combined with the `customInstructions` property

---

## Configuration Precedence

Mode configurations are applied in this order:

1. **Project-level** (from `.mirrormodes`)
2. **Global** (from `custom_modes.yaml`, then `custom_modes.json`)
3. **Default** (built-in)

**Important:** Project modes **completely override** global modes with the same slug — no properties are merged. If you have a global 'code' mode and a project-specific 'code' mode, the project version wins entirely.

## Overriding Default Modes

You can override built-in modes (Code, Debug, Ask, Architect, Orchestrator) with customized versions by creating a mode with the same slug.

### Overriding Modes Globally

To customize a default mode across all projects:

1. Open the **Modes** page → click Mode menu → click <Codicon name="settings-gear" />
2. Click "Edit Global Modes"
3. Add your override:

**YAML Example:**
```yaml
customModes:
  - slug: code
    name: 💻 Code (Global Override)
    roleDefinition: You are a software engineer with global-specific constraints.
    groups:
      - read
      - - edit
        - fileRegex: \.(js|ts)$
          description: JS/TS files only
```

### Project-Specific Mode Override

To override a default mode for one project:

1. Open the **Modes** page → click "Edit Project Modes (.mirrormodes)"
2. Add your override:

**YAML Example:**
```yaml
customModes:
  - slug: code
    name: 💻 Code (Project-Specific)
    roleDefinition: You are a software engineer with project-specific constraints.
    groups:
      - read
      - - edit
        - fileRegex: \.py$
          description: Python files only
      - command
```

**Common Use Cases for Overriding:**
- Restricting file access to specific types
- Specializing behavior for your tech stack
- Adding custom instructions for project standards
- Removing tools to prevent unwanted operations

## Understanding Regex in Custom Modes

Regular expressions (`fileRegex`) control which files a mode can edit.

:::tip
**Let Mirror Build Your Regex Patterns**

Ask Mirror:
```
Create a regex pattern that matches JavaScript files but excludes test files
```
Mirror generates the pattern for you. Adapt for YAML (single backslashes) or JSON (double backslashes).
:::

**Important Rules:**
- **JSON:** Backslashes must be double-escaped (e.g., `"\\.md$"`)
- **YAML:** Single backslash is usually sufficient (e.g., `\.md$`)
- **Path Matching:** Patterns match against the full relative file path from workspace root
- **Case Sensitivity:** Regex patterns are case-sensitive by default
- **Validation:** Invalid patterns are rejected with an error message

**Common Pattern Examples:**

| Pattern (YAML-like) | JSON `fileRegex` | Matches | Doesn't Match |
| ------------------- | ---------------- | ------- | ------------- |
| `\.md$` | `"\\.md$"` | `readme.md`, `docs/guide.md` | `script.js` |
| `^src/.*` | `"^src/.*"` | `src/app.js` | `lib/utils.js` |
| `\.(css\|scss)$` | `"\\.(css\|scss)$"` | `styles.css`, `theme.scss` | `styles.less` |
| `docs/.*\.md$` | `"docs/.*\\.md$"` | `docs/guide.md` | `guide.md` |

**Key Regex Building Blocks:**
- `\.` — Matches a literal dot (YAML: `\.`, JSON: `\\.`)
- `$` — End of string
- `^` — Beginning of string
- `.*` — Any character, zero or more times
- `(a|b)` — Match a or b

**Testing Your Patterns:**
1. Test on sample file paths using an online regex tester
2. Remember escaping rules for JSON vs YAML
3. Start simple and build complexity

## Additional Features

### Built-in Mode Customization
When exporting built-in modes, any customizations you've made are included. Share your personalized versions with others.

### Mode Deletion and Rules
When deleting a mode through the UI, Mirror VS prompts you about deleting the associated rules folder. Helpful guard against accidental data loss.

### Global Rules Directory
There's also a generic `.mirror/rules/` directory (without mode suffix) for shared rules across all modes.

### Troubleshooting

**Common Issues:**
- **Mode not appearing:** You may need to reload VS Code after creating or importing a mode
- **Invalid regex patterns:** Test patterns before applying them
- **Precedence confusion:** Project modes completely override global modes with the same slug — no merging
